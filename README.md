# Intelligent IT Ticket Auto-Resolution System

A working prototype of an AI system that classifies IT support tickets and
instantly suggests resolutions — built to satisfy the constraints of the
assignment:

| Constraint | How it's addressed |
|---|---|
| 2M tickets/month, 5,000 issue types | Hierarchical (coarse → fine) classification, so no single model ever chooses among 5,000 classes at once |
| 30% noisy/poorly written tickets | Text-normalization preprocessing layer + models trained on typo-injected data |
| 10% tickets are screenshots | OCR layer (Tesseract) converts image → text before classification, with confidence-based fallback |
| Response time < 2 seconds | Lightweight TF-IDF + linear models, no network calls at inference time (~3–7ms per ticket measured locally) |
| Classification accuracy ≥ 80% | Confidence-threshold escalation: low-confidence tickets are routed to a human instead of guessed, so accuracy on auto-resolved tickets stays high |

> **Note on scale:** this repo ships with a synthetic dataset (1,200 tickets,
> 5 coarse categories, 15 issue types) so it's fast to train/demo/deploy
> without a GPU or external model downloads. The architecture — hierarchical
> classification + nearest-neighbor solution retrieval + confidence-based
> escalation — is the same shape you'd run at 2M tickets/5,000 issue types;
> see "Scaling to production" below for what changes.

## Architecture

```
Ticket (text / screenshot)
        │
        ▼
 ┌─────────────────────┐
 │ OCR (if screenshot) │  app/ocr.py
 └─────────────────────┘
        │
        ▼
 ┌─────────────────────┐
 │ Text normalization  │  app/preprocessing.py
 │ (typo fixes,cleanup)│
 └─────────────────────┘
        │
        ▼
 ┌─────────────────────┐
 │ Stage 1: coarse     │
 │ category classifier │  app/classifier.py
 └─────────────────────┘
        │
        ▼
 ┌─────────────────────┐
 │ Stage 2: fine issue-│
 │ type classifier     │
 │ (per-category model)│
 └─────────────────────┘
        │
        ▼
 ┌─────────────────────┐
 │ Confidence check    │
 │  low → escalate to  │
 │       human agent   │
 │  high → continue    │
 └─────────────────────┘
        │
        ▼
 ┌─────────────────────┐
 │ Solution retrieval  │  app/retrieval.py
 │(nearest past tickets│
 │ of same issue type) │
 └─────────────────────┘
        │
        ▼
   Suggested resolution + similar past tickets
```

## Repo layout

```
app/
  main.py          FastAPI app: /health, /classify, /classify_image, /metrics
  classifier.py     Hierarchical classifier (coarse -> fine)
  retrieval.py      TF-IDF nearest-neighbor solution retrieval
  preprocessing.py  Noisy-text normalization
  ocr.py            Screenshot -> text (Tesseract), with confidence fallback
data/
  generate_data.py  Synthetic ticket dataset generator
  tickets.csv        Generated dataset (1,200 tickets)
train.py             Trains classifier + builds retrieval index -> artifacts/
evaluate.py          Stress-test evaluation on fresh, noisier data
tests/test_api.py    API tests (pytest)
Dockerfile           Container build (installs tesseract, trains at build time)
Procfile / render.yaml  Deployment configs for Render/Heroku-style platforms
```

## Running locally

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python data/generate_data.py   # generates data/tickets.csv
python train.py                 # trains classifier + retriever -> artifacts/
python evaluate.py               # optional: stress-test accuracy/latency

uvicorn app.main:app --reload --port 8000
```

Then:

```bash
curl -X POST http://localhost:8000/classify \
  -H "Content-Type: application/json" \
  -d '{"text": "vpn keps disconecting evry few minuts pls help asap"}'
```

```json
{
  "coarse_category": "Network",
  "issue_type": "vpn_connection_failure",
  "confidence": 0.529,
  "should_escalate_to_human": false,
  "suggested_resolution": "Restart the VPN client, confirm correct server region...",
  "similar_past_tickets": [ ... ],
  "response_time_ms": 6.79
}
```

For a screenshot ticket:

```bash
curl -X POST http://localhost:8000/classify_image \
  -F "file=@screenshot.png"
```

Interactive API docs are auto-generated by FastAPI at `/docs` once running.

## Deployment

**Docker (works anywhere):**
```bash
docker build -t it-ticket-resolver .
docker run -p 8000:8000 it-ticket-resolver
```

**Render / Heroku-style platforms:** use `render.yaml` / `Procfile` as-is —
push the repo and connect it; the build command trains the model as part
of the build step.

**GitHub:** push this whole directory as-is; `artifacts/*.joblib` is
gitignored (regenerated by `train.py` during build), keeping the repo small.

## Design decisions & tradeoffs

- **Hierarchical over flat classification** — with 5,000 issue types, a flat
  classifier either underfits rare classes or needs a huge model. Splitting
  into coarse category → fine issue type turns one hard 5,000-way problem
  into many easy 10–50-way problems, which is both more accurate and easier
  to retrain per-category as new issue types appear.
- **TF-IDF + linear SVM instead of a transformer** — meets the <2s latency
  budget with no GPU and no external model download (this environment has
  no access to Hugging Face Hub). In production, swapping in a fine-tuned
  DistilBERT/MiniLM encoder for Stage 1 would improve robustness to
  paraphrasing and multilingual tickets, at the cost of needing GPU serving
  infrastructure (still comfortably under 2s with batching).
- **Confidence-threshold escalation** — rather than force every ticket
  through a guess, we calibrate probability estimates (`CalibratedClassifierCV`)
  and route anything below threshold to a human agent. This is what actually
  lets the system hit "≥80% accuracy" as a promise about auto-resolved
  tickets, rather than an unenforceable average over ambiguous inputs.
- **Retrieval instead of generation for solutions** — resolutions come from
  the historical knowledge base attached to the predicted issue type (plus
  similar past tickets as evidence), not from an LLM generating free text.
  This avoids hallucinated instructions and is deterministic/auditable,
  which matters for IT support where a wrong suggested fix has real cost.

## Scaling to production (2M tickets/month, 5,000 issue types)

| Component | Prototype (this repo) | Production |
|---|---|---|
| Text embedding | TF-IDF | Fine-tuned DistilBERT/MiniLM encoder |
| Classifier | LinearSVC per level | Same hierarchical structure; transformer + lightweight classification head |
| Solution retrieval | TF-IDF cosine similarity | FAISS/Milvus ANN index over transformer embeddings |
| Serving | Single-process Uvicorn | Autoscaled inference pods behind a queue (Kafka/SQS), with ONNX-optimized models |
| OCR | Local Tesseract | Tesseract or managed OCR (AWS Textract) with async processing for image tickets |
| Monitoring | `evaluate.py` script | Prometheus/Grafana tracking per-category accuracy, escalation rate, p95/p99 latency, and drift alerts |
| Retraining | Manual `python train.py` | Scheduled retraining pipeline fed by agent-corrected labels |
